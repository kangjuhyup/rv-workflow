# Brainstorming

Use only when the user explicitly requests brainstorming or when a product decision is genuinely unresolved. First inspect the relevant repository context, then identify the goal, constraints, success criteria, and boundaries. Ask one focused question at a time only when its answer materially changes the design.

Offer two or three viable approaches with tradeoffs and a recommendation. Keep the design proportional to the task: architecture, interfaces, data flow, failure behavior, and verification only where they matter. Present the design in reviewable sections and wait for acceptance before treating it as an implementation contract. Do not use brainstorming to stall a clear request or expand its scope.
